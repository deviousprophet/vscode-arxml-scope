# Testing Guidelines

Conventions this project has actually been burned by. Every rule below has a real defect behind it —
several of them shipped past a first review before being caught.

## An assertion must fail when the feature is deleted

Before trusting a new test, break the feature it covers and watch the test fail. A test that passes
either way is worse than no test, because it is counted as evidence.

The real example: the criterion "a normally-opened `.arxml` still uses the text editor" was tested by
calling `vscode.window.showTextDocument`, which **forces** a text editor. The assertion could never
fail. It now opens the file with `vscode.open`, and flipping the custom editor's manifest `priority`
from `"option"` to `"default"` makes it fail.

The same applies to a manifest value: asserting that `package.json` says `"option"` proves the field
was copied, not that the editor does not take over. Pair it with a behavioural test.

## Fixtures are pinned, and line endings are part of the contract

`src/test/fixtures/**` and `reference/**` are pinned with `-text` in `.gitattributes`. This machine has
`core.autocrlf=true`, so without the pin a fixture's LF/CRLF would flip between machines and tests that
assert exact bytes would fail somewhere else but not here.

When adding a fixture that asserts line endings, put it under that glob. **Never "fix" a failing
line-ending assertion by changing the fixture** — the fixture is the contract.

## Expected models are hand-authored, never generated by the code under test

`src/test/expected/*.json` is written by hand from the legacy rules. A snapshot produced by the scanner
proves only that the scanner is deterministic, not that it is correct; it would happily agree with
itself about a wrong offset.

The same holds for the editing fixtures' `.expected.arxml` files: derive them from the input and the
documented write rules, and re-derive at least one by hand during review.

## Editing tests operate on a copy, never on a committed fixture

A test that edits its own fixture passes once, then fails forever and silently rewrites the
repository. Copy the fixture into a temporary directory, edit the copy, and compare bytes there.

Prove the isolation rather than assuming it: hash the committed fixtures, run the suite more than once,
and hash again.

## Write paths are asserted on bytes, not on values

For anything that writes, the criterion is that **nothing else in the file moved**. Compare the whole
file against an expected file and confirm the difference is one contiguous span. A value-level
assertion ("the model now says 42") passes even when the writer has corrupted the surrounding markup.

## The refusal path is asserted too

Validation in front of a write is only worth what its refusal test proves. For every refusal path —
invalid value, XML-illegal character, a region that no longer resolves, a region whose bytes moved
since the edit was prepared — assert on the text, the on-disk bytes **and** the dirty flag, so a
partial write cannot hide behind a message.

## Running the tests

| Purpose | Command |
|---|---|
| Everything | `npm test` |
| Types only | `npm run check-types` |
| Lint only | `npm run lint` |
| Core suites only | `npm run compile-tests` then `npx mocha --ui tdd "out/test/core/*.test.js"` |

`npm test` drives a real VS Code instance through `vscode-test`, so the first run downloads VS Code
into `.vscode-test/` (gitignored). If that download is blocked by a proxy, the failure is environmental
— check before assuming a code defect. The suite uses the **TDD** mocha UI: plain `npx mocha` fails
with `suite is not defined`.

There is no webview DOM in the test host. Webview behaviour is therefore asserted at the level of the
rendered HTML string, and anything that depends on real DOM interaction has to be confirmed by hand —
say so in the task notes rather than implying it was tested.

# Testing Guidelines

Conventions this project has actually been burned by. Every rule below has a real defect behind it —
several of them shipped past a first review before being caught.

## An assertion must fail when the feature is deleted

Before trusting a new test, break the feature it covers and watch the test fail. A test that passes
either way is worse than no test, because it is counted as evidence.

The real example: the criterion "a normally-opened `.arxml` still uses the text editor" was tested by
calling `vscode.window.showTextDocument`, which **forces** a text editor. The assertion could never
fail. It now opens the file with `vscode.open`, and flipping the custom editor's manifest `priority`
from `"option"` to `"default"` makes it fail.

The same applies to a manifest value: asserting that `package.json` says `"option"` proves the field
was copied, not that the editor does not take over. Pair it with a behavioural test.

## Fixtures are pinned, and line endings are part of the contract

`src/test/fixtures/**` and `reference/**` are pinned with `-text` in `.gitattributes`. This machine has
`core.autocrlf=true`, so without the pin a fixture's LF/CRLF would flip between machines and tests that
assert exact bytes would fail somewhere else but not here.

When adding a fixture that asserts line endings, put it under that glob. **Never "fix" a failing
line-ending assertion by changing the fixture** — the fixture is the contract.

## Expected models are hand-authored, never generated by the code under test

`src/test/expected/*.json` is written by hand from the legacy rules. A snapshot produced by the scanner
proves only that the scanner is deterministic, not that it is correct; it would happily agree with
itself about a wrong offset.

The same holds for the editing fixtures' `.expected.arxml` files: derive them from the input and the
documented write rules, and re-derive at least one by hand during review.

## Editing tests operate on a copy, never on a committed fixture

A test that edits its own fixture passes once, then fails forever and silently rewrites the
repository. Copy the fixture into a temporary directory, edit the copy, and compare bytes there.

Prove the isolation rather than assuming it: hash the committed fixtures, run the suite more than once,
and hash again.

## Write paths are asserted on bytes, not on values

For anything that writes, the criterion is that **nothing else in the file moved**. Compare the whole
file against an expected file and confirm the difference is one contiguous span. A value-level
assertion ("the model now says 42") passes even when the writer has corrupted the surrounding markup.

## The refusal path is asserted too

Validation in front of a write is only worth what its refusal test proves. For every refusal path —
invalid value, XML-illegal character, a region that no longer resolves, a region whose bytes moved
since the edit was prepared — assert on the text, the on-disk bytes **and** the dirty flag, so a
partial write cannot hide behind a message.

## Running the tests

| Purpose | Command |
|---|---|
| Everything | `npm test` |
| Types only | `npm run check-types` |
| Lint only | `npm run lint` |
| Core suites only | `npm run compile-tests` then `npx mocha --ui tdd "out/test/core/*.test.js"` |

`npm test` drives a real VS Code instance through `vscode-test`, so the first run downloads VS Code
into `.vscode-test/` (gitignored). If that download is blocked by a proxy, the failure is environmental
— check before assuming a code defect. The suite uses the **TDD** mocha UI: plain `npx mocha` fails
with `suite is not defined`.

There is no webview DOM in the test host. Webview behaviour is therefore asserted at the level of the
rendered page: the static shell, the escaped row JSON, the CSS, and the page's own inlined functions
extracted with `scriptTestUtils` and compiled. Pure row/flatten/filter/window behaviour is tested
directly; anything that depends on real DOM interaction has to be confirmed by hand or in the browser
harness — say so in the task notes rather than implying it was tested.

## A browser harness is not a webview

`npm run preview:ecuc` serves the production `renderHtml` page in the in-app browser with a stubbed
`acquireVsCodeApi` and stubbed `--vscode-*` variables. That is enough to observe layout, hover, focus,
scroll, filter passes and the inspector with a real DOM — much more than a string assertion. It is
still **not** a VS Code webview: it cannot prove VS Code's own theme resolution, the real custom-editor
tab/column/focus behaviour, or accessibility-tree exposure. Record harness observations as
harness-observed, and keep the real-host rows in the task's manual table.

The harness must wrap the production renderer; a second renderer is a test that agrees with itself.
`npm run preview:check` asserts that each wrapped page contains the production row JSON and the
virtual shell (spacers, window, inspector, empty state), plus the stub and theme variables. The row
JSON is compared against `buildRows`, not against a full-tree string.

## The reference must be the post-processed output

The remote `ref/ecucvalues-for-vscode` branch's `.artext` is produced by `mmx` + `Arxml2Artext.mm`
and then transformed by `postProcessArtextGen`, which collapses whitespace inside `[...]`
(`[(A == B)]` → `[(A==B)]`). Comparing the raw `mmx` output is not comparing the reference. Capture
the post-processed file and the exact command in the task research, and keep the raw/pre-processed
state described in the README. The capture is evidence for the look; it is never a product fixture
and is not read by the renderer.

## Document view tests drive the page's own helpers

Document markup/CSS tests are string assertions (the Document-only shell, layout/geometry, token
selectors, fallbacks, no Tree/line-number/copy code), but the view/details behaviour must drive the
page's own `applyInspectorVisibility`, `subtreeRowIds`, `guidesFor`, `reconcileRowState` and
`detailsValueInput` extracted with `scriptTestUtils` against stub elements — not a host-side twin.
The mutation table for this pass is: re-add a Tree toggle/view state, Tree CSS/glyph/probes; re-add
the line-number gutter/`data-line`/digits; re-add the repeating indent gradient; drop the
bracket-guide computation or leak it to every row; drop brace hover; re-add inline `.value` editing;
re-add the F2 pseudo hint; re-add the details Source row or a Copy action; drop the details edit post;
re-add digits to the re-scan; switch the container accent; make every reference followable; leak the
selected subtree; remove the collapse/expand labels or the twisty's row-height hit area; re-add the
gutter-era scroll padding; re-add the high-contrast subtree fill; discard a pending details draft;
put the twisty back inline; replace the Codicon chevron with a filled triangle; shrink the 26px
gutter; show expanded chevrons at rest; re-add the `=` to a reference tooltip; drop the DEST capture;
treat every numeric as integer; remove the format padding; put `(= 0x…)` back in a row; re-add a
Document follow link; hide the details Jump button; use a text input for Boolean; drop the input
sanitizer; each mutation must fail a test. A CSS selector assertion
is still not a rendered-layout test, so pair it with the dark/HC/selected parameter/selected
container/guide-hover/details/narrow/deep captures and a browser pass. Assertions and captures must
match the production CSS, never the prototype file. There is no source-line gutter to conflate; the
row model carries no source-position fields.

## Virtual page tests drive the page's serialized row code

The virtual row renderer is tested at two levels. Pure modules (`renderRows`, `virtualScroll`,
`filterRows`/`flattenRows`) have ordinary unit tests over values. The page's own copy is extracted
from `renderHtml` with `scriptTestUtils` and compiled: `filterRows`, `flattenRows`,
`inspectorFields`, `reconcileRowState`, `resolveFocusId`, `subtreeRowIds`, `guidesFor` and the
virtual math are driven with real row data, so the page does not get a second implementation.
`virtualPage.test.ts` pins the window range and overscan, the bounded row count, collapse/filter
display lists, the selected subtree, the offscreen inspector, focus restoration and the re-scan
payload. Structural
assertions (a window loop, spacers, no `innerHTML`/style attribute in the row builder, `data-level`
CSS) are the regression guard; the real DOM pass is the browser harness.

Mutation checks for this layer: render the full row list instead of `[start,end)`, remove the
top/bottom spacers, zero the overscan, drop subtree collapse/filter-ancestor logic, drop the filter
generation guard, use `innerHTML` for row text, use an inline depth style, remove
`aria-level`/posinset/setsize, remove focus restore, send full HTML on re-scan, use
`#tree-window` as the offset, leak bracket guides outside their container, or leak the subtree tint
to siblings; each must fail a test. Prefer the
page's own functions over a grep-only assertion, and record which checks were browser-observed rather
than unit-tested.

## A CSS rule is not a contrast measurement

Asserting that `.node[data-selected] .value` names a `--vscode-*` variable proves the rule exists, not
that the text is readable. An earlier light-theme pass had a green value on the blue selection at
**1.33:1** while the rule looked correct — one reason that pass was dropped. Measure the computed
foreground/background in the browser harness and record the ratio; keep the CSS assertion as a
regression guard.

## Source-level wiring assertions are a last resort

The provider's `{ type: 'copy' }` branch and clipboard module were removed with the details Copy
actions. The remaining source-level wiring is the details editor's `{ type: 'edit' }` post and the
re-scan handler; the input's Enter/Escape/Tab and refusal behaviour are asserted through the page's
own serialized functions and browser captures, while the provider write is behaviourally tested.
When you use a source assertion, say so in the task notes; do not present it as a behavioural test.

## Samples and benchmarks are evidence

`npm run samples:ecuc` writes synthetic ECUC files to `../sample` (outside the repository) and
`npm run perf:ecuc -- <file>` measures the scanner, node index and renderers in Node. The sample files
are not committed; the generator and benchmark are dev-only. `preview:check` must not include the
local sample directory, or CI would depend on a developer's disk.

A benchmark is evidence, not a promise. It does not cover browser layout/paint or a real VS Code
webview; record the browser page observation separately. A single huge-file run is not a reason to add
virtualisation. The sample generator is deterministic and the generated files are synthetic; never
point it at a real customer directory.

## The page's own helpers are the ones under test

When a rule lives in the inlined page script, extract the page's copy with `scriptTestUtils` and drive
it, rather than testing a host-side twin. `prepareFocus`'s initial-selection adoption is tested with a
stubbed DOM in `uxPolish.test.ts`; the mutation "remove the adoption" fails it. A test that only greps
for a call site can pass with the feature deleted.
